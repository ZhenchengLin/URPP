# URPP — Local Numeric Teaching CLI V0.1

Status: Implementation 13E-3C.
Roadmap: Week 4 — Adaptive Teaching.

## Why a CLI

At the start of this implementation, the existing
FastAPI application exposed only the health route.

The frontend directory contained only a README.

Rather than treating a test Presenter as an actual
application integration, this stage establishes
one executable, local teaching interaction.

It is a terminal application, not a browser frontend.

## Scope

The CLI runs one synthetic arithmetic lesson in
a new, isolated SQLite database.

It uses the existing:

- Assessment Item Repository.
- Recoverable Numeric Session.
- Evidence-driven Teaching Orchestrator.
- Assistance Presentation Service.
- Assistance Event Log.
- Student State recovery pipeline.

The question and teaching content are static demo
materials, not generated by an external LLM.

The synthetic item alignment does not establish
review of any real student's assessment.

## Actual presentation integration

The TerminalAssistancePresenterV01 writes the
requested Hint or Solution to the process output
stream and flushes it.

After the output operation succeeds, it returns
True to the existing Presentation Service.

The Presentation Service then requests persistence
of an application-reported Assistance Event.

Terminal output does not prove that the student
read, understood, or attended to the content.

The application remains unauthenticated and
must not be exposed as a production student API.

## Failure semantics

The Presentation Service checks that the Assignment
is pending before invoking the Presenter.

The Assistance Event Repository independently
checks pending status before writing the event.

If the Presenter fails, the Service does not
intentionally create a new Assistance Event.

If presentation succeeds but logging fails, the
CLI stops the lesson and reports that assistance
may have been provided without a durable record.

The CLI does not automatically replay assistance
after this partial operation.

This is not an exactly-once delivery guarantee.

## Submission recovery and decision timing

The existing Numeric Session submission method may commit
an Attempt before rejecting an as_of timestamp that is
slightly earlier than the repository-generated submission
timestamp.

For that specific post-commit error, the local CLI recovers
the saved result with resume() using a fresh current
timestamp. It does not submit the answer again.

The next teaching decision uses the recovered Student State
snapshot's as_of timestamp as its requested_at timestamp.

This preserves the existing rule that a teaching decision
cannot precede the Student State snapshot on which it is
based.

These are local CLI integration rules. The existing
repository, scoring, and State Estimator contracts remain
unchanged.

## Student State and provenance

The Attempt's assistance_level and
prior_solution_exposure remain unknown.

The presence of a Hint or Solution record does
not automatically create eligible performance
evidence.

The absence of such records does not prove that
the student received no external assistance.

A correct answer in this demo cannot establish
verified independent success.

The existing evidence eligibility and state
estimation rules remain unchanged.

## Database safety

The CLI requires an explicit database path.

It creates a new SQLite file using exclusive
creation and refuses existing files.

The new file is created with restrictive
owner-only permissions where supported.

SQLAlchemy metadata initialization is limited
to this new demo database.

The CLI never opens an existing application
database, runs a migration on it, or modifies
a real student's records.

## End-to-end tests

The test suite launches the CLI in a separate
Python process.

It sends terminal inputs through stdin and
inspects the resulting SQLite database after
the CLI process exits.

Tests cover:

- Hint presentation followed by answer submission.
- Solution presentation.
- Answer submission without recorded help.
- Refusal to overwrite an existing database.
- Quitting with an Assignment still pending.
- No fabricated independent success.

## Future browser integration

A future stage can implement an actual frontend
and application-owned API.

That work will require a separately reviewed
student/session access boundary, request handling,
presentation acknowledgment policy, database
lifecycle, and assistance-provenance contract.

This CLI does not supply those production features.
